# 管理者画面の定義

運用者(adminロール)が「異常の有無」と「次に何をすべきか」を判断できる画面の定義。
実装前の合意事項として残す。決めた理由も併記する(後から読む人が同じ判断に至れるように)。

## 目的と利用者

- **目的**: サーバーの健康状態を1箇所で把握できること。いまは機能ごとのモーダルはあるが、
  「このサーバーは正常か」を見る場所が無く、`podman inspect` や journald を見ないと分からない
  情報が多い。**SSHできない状況でも判断できること**を重視する。
- **利用者**: adminロールのみ。DBの内部状態・容量・破損情報は運用情報であり、
  アクセス許可ユーザー画面と同じ扱いにする。

## 画面の出し方

**モーダルではなくページ切替**。タブが増える前提でモーダルにすると、幅・スクロール・
情報量のすべてで無理が出る。

**共通アーキテクチャの「管理機能の画面」の形にそろえる**(共通アーキテクチャ資料の 画面 8 章・構成 6.2〜6.4)。
どのサービスでも、管理の情報は同じ形の WebAPI で返し、画面の並びと見た目をそろえる。

- 管理の画面は、文書一覧とは**別のページ**(`app/static/admin.html`)。デザインテンプレート(Template01)の
  `template_admin.html` を写して作った。テンプレートの CSS(`components.css` など)は `body` などページ全体に効くため、
  文書一覧と同じページには入れられない(入れると文書一覧の見た目が崩れる)。
- 共通の 4 つのタブの中身は `app/static/admin/admin.js` が描く。元はデザインテンプレートの見本(16d55c2)から写した物で、
  **いまは Document Manager の実装として持つ**(`ui.js`・`dev_mode.js` も同じ)。デザインテンプレートは見た目のテンプレートで、
  実装の方法までは決めない(利用者の判断)。直すときは、ここで直す。見た目(CSS)は、デザインテンプレートの物を使う。
- 独自のタブ(データベース・変換サービス・Miro 連携)は `admin-page.js` が、テンプレートの部品(表・バッジ・モーダル)で描く。
  開いたときに初めて読む(開いていないタブのために問い合わせない)。
- 入口は上部バーの歯車(admin にだけ出す)。管理の画面のヘッダーに「文書一覧へ戻る」を置く。
- 開いたときに `api/check_access_token` で確かめる。ログインしていなければ戻り先つきでログインの画面へ移り、
  管理者でなければ中身を出さず、共通のスクリプトも読み込まない。仮に読み込んでも WebAPI が 403 を返す。
- **タブは `?tab=` で開ける**(切り替えると URL に残り、再読み込みでも同じタブ)。Miro の許可の画面からの戻り先も
  `admin.html?tab=miro` にした。
- ページのスクリプトは全部外のファイルにし、`script-src 'self'` の CSP で配る(監査ログや利用者の一覧には、利用者が書いた文字が出るため)。

## タブ構成

| タブ | 中身 | 描く物 |
|---|---|---|
| 利用者 | 台帳(メールアドレスと権限)の追加・権限の変更・削除、最終ログイン。最後の管理者は下げも外しもできない(409)。外すとセッションと APIキーも止める | 共通(admin.js) |
| セッション | 利用者ごとのセッション・APIキーの一覧、利用者単位の切断、切断の履歴 | 共通(admin.js) |
| 監査ログ | 全員ぶんの操作の記録を、期間・利用者・操作・対象で探す(下記) | 共通(admin.js) |
| サーバー | 設定(**APIの回数の上限**・**機能のOn/Off**)/ このサーバー(版・リビジョン・ビルド時刻・起動時刻・稼働時間・DB の種類とファイル・同梱クライアントの版・DB の整合性)/ **接続の確認**(届くか・掛かった時間・最後に届いた時刻)/ **セキュリティ設定** / **動いている部品の版** / **部品表** | 共通(admin.js) |
| データベース | 整合性確認(簡易・厳密)と最終結果、**DBと実ファイルの照合** | 独自(admin-page.js) |
| 変換サービス | 2 つの変換サービスの到達性・版・上限、変換に失敗した文書の一覧と再実行 | 独自(admin-page.js) |
| Miro 連携 | Miro のアプリの値(環境変数か画面で入力)/ 連携・連携し直し・解除 / 書き出すボードの選択([miro.md](miro.md))。アプリの値を画面で入れられるので、管理者には常に出す | 独自(admin-page.js) |

### 監査ログ

`audit_log`(本人の操作履歴と同じ表)から、全員ぶんを読む。行ごとに、結果(`success` / `denied` / `failed`)・
経路(`screen` / `apikey`)・APIキーの権限・接続元の IP を残す(列を足す前の行は、成功・経路と IP は不明として返す)。

| 残す物 | 補足 |
|---|---|
| ログイン | 台帳に無くて断ったものも(`denied`) |
| 文書・モックアップの書き込み | 登録・新しい版・アーカイブ・復元・プロジェクトへの配置・関連づけ・版のつなぎ・別名の付け替え・照合からの登録 |
| 管理の操作 | 利用者の追加・権限の変更・削除、切断、機能の切り替え、回数の上限、意味検索と Miro 連携の設定、DB の整合性の確認(重い確認を実行したことを残す) |
| 権限で断った呼び出し(403) | 同じ人の同じ口は 1 分に 1 回だけ(DB を溢れさせない) |

文書のダウンロードは残さない(数が多い。標準出力のログには残る)。本人の操作履歴(`api/history`)は、今までどおり文書と
プロジェクトの操作だけを並べる(管理の操作やログインは混ぜない)。

**バックアップのタブは作らない**。空のタブや「準備中」は、あるように見えて無いので害になる。

### 移設しないもの

| | 理由 |
|---|---|
| APIキー管理 | 全員が使う。管理ページに入れるとadmin専用と誤解される |
| タグ体系の管理 | 文書一覧の文脈に属する |
| 操作履歴 | 自分の操作だけで、管理機能ではない |
| ベクトル索引 | 既に独立ペインがある。動いているものを動かさない(将来タブへ統合する余地はある) |

## 管理の WebAPI(共通の形)

名前と応答の形は、共通アーキテクチャ(構成 6.3・6.4)のとおり。道の頭だけ Document Manager の慣習(`api/`)にしてある。
いずれも `requireAdmin`(APIキーは admin になれないので、APIキーでは呼べない)。旧い口(`api/allowed_users`・`api/sessions`・
`api/rate-limit`・`api/features`)は、Skill や結合試験が使うので残す(最後の管理者を守る決まりと監査ログは同じ)。

| API | 返す物・受ける物 |
|---|---|
| `GET api/admin/users` | `{users: [{email, role, addedBy, addedAt, lastLoginAt}], roles: [{value, label}], self}` |
| `POST api/admin/users` | `{email, role}`。形の違うメールアドレス・知らない権限は 400、もう居れば 409 |
| `PUT api/admin/users/{email}` | `{role}`。台帳に無ければ 404、最後の管理者を下げるのは 409 |
| `DELETE api/admin/users/{email}` | 外して `{email, sessions, apiKeys}` を返す(止めた数)。最後の管理者は 409 |
| `GET api/admin/sessions` ・ `/history` ・ `POST /revoke` | `api/sessions` と同じ処理 |
| `GET api/admin/audit` | `?range=1d\|7d\|30d&user=&action=&target=&before=` → `{entries: [{id, at, user, action, target, result, via, keyRole, ip}], actions, limit, nextBefore}` |
| `GET api/server-status` | 版・起動時刻・DB に加えて `rateLimit`・`features`・`security`・`extra` |
| `PUT api/server-status/rate-limit` | `{authenticated \| anonymous: 回数}` → 新しい `rateLimit`。範囲の外は 400 |
| `PUT api/server-status/features/{key}` | `{enabled}`。構成で決まる機能は 400、知らない機能は 404 |
| `GET api/server-status/components` | 相手ごとに `configured`・`reachable`・`latencyMs`・`lastSuccessAt`・`error`・製品と版・土台 |

## 独自のタブの API

いずれも `requireAdmin`。

| API | 用途 |
|---|---|
| `GET api/server-status` | 版・リビジョン・ビルド時刻・起動時刻・稼働秒・DBバックエンド・DBファイル名とサイズ |
| `GET api/office-render/health` | 変換サービスの到達性(既存の `checkHealth()` を画面から見えるようにする) |
| `GET api/html-pdf/health` | PDFでダウンロード用の変換サービス(pdf-converter)の到達性。Office用とは別のコンテナなので、同じタブに別々に出す |
| `GET api/storage-reconcile` | DBと実ファイルの照合(下記) |
| `POST api/storage-reconcile/restore` | 実ファイルだけある文書をDBへ登録し直す |

`GET api/documents?renderStatus=failed` も足す。いまは絞り込みが無く、変換に失敗した文書を
探す手段が無い。これは readonly 権限のままにする(AIからも「変換に失敗した資料ある?」に
答えられるようになる)。

起動時刻は `api/version` には載せない。あちらは**公開**エンドポイントであり、
スキャンに余計な材料を与えない。

## 動作の原則

- **画面を開いただけでは重い処理を走らせない**。整合性確認と照合はボタン。開いた時点では
  起動時に実行した結果を表示する(サーバー側で最後の結果を保持する)。
- **重い操作は正体を明かす**。厳密な整合性確認は better-sqlite3 が同期APIのため
  サーバーの他の処理が止まる。確認ダイアログで明示し、業務時間外を勧める。
- **破壊的な操作は置かない**。復旧・再構築・DBの直接編集は画面に入れない。
  バックアップからの復旧はサーバー作業とする(誤操作の被害が大きすぎる)。

## DBと実ファイルの照合

### 背景: 孤立ファイルは定常的に生まれる

アップロードは「先にファイルを書き、後からDBへ登録する」順序で、
**途中で失敗したときの後始末が無い**(catch節はログを出して500を返すだけ)。
`app/lib/storage.js` には削除APIが存在しない。

つまり「実ファイルはあるのにDBに無い」は、失敗したアップロードのたびに増える。
この機能はまれな事故の保険ではなく、**日常的な掃除**も兼ねる。

→ 入口を直す(失敗時に書いたファイルを消す)ほうが根本的。ただし storage に削除APIを
足す必要があり、S3側の扱いも決まっていないため別項目とする(下記の積み残し)。

### 扱い

| 状態 | できること |
|---|---|
| 実ファイルだけある | **復元**(DBへ登録し直す)。判断材料として更新日時・サイズ・ファイル名・preview/renderの有無を出す |
| DBだけある | **報告とラベル付けのみ。削除は置かない** |

**削除しない理由**: ボリュームが未マウントのときは全件が欠損に見える。自動クレンジングは
「復旧可能な障害」を「恒久的なデータ消失」に変えてしまう。しかも失われるのはタグ・メモ・
版の鎖・アップロード者で、**ファイルからは絶対に再生できない唯一の情報**である。

### 復元の扱い

- **アーカイブ済みとして登録する**。元がアーカイブ済みだったか知る手段がないため、
  現役として復活させると一覧が汚れ、版の鎖も壊れて見える。アーカイブなら一覧は汚れず、
  必要なら既存の復元操作で戻せる。
- 全文検索テキストは再抽出する。ベクトル索引は未処理として登録し、通常の流れで追いつかせる。
- `uploaded_by` はシステム値、`uploaded_at` はファイルの更新時刻(IDの年月で妥当性を確認)。
- タグ・メモは空。

### 必須のガード

- **ストレージに到達できていない疑いがあるときは、何も報告しない**。`documents` ディレクトリが
  存在しない、または空なのにDBに大量の行がある場合は、「差異」ではなく「障害」として
  警告だけ出して照合を中止する。**これが無いとこの機能自体が凶器になる**。
- 第一弾は **local ストレージのみ対応**。S3/GCSは一覧取得のコストとページングが別問題に
  なるため、未対応を画面に明示する。
- 走査は読み取りのみ。件数上限とページングを設ける。

### 名前

画面では「**DBと実ファイルの照合**」とする。「クレンジング」は削除を含意するため使わない。
消す機能が無いのに消す語を使うと、利用者の期待と操作が食い違う。

## 積み残し

| 項目 | 理由 |
|---|---|
| バックアップ(整合スナップショット) | DB種別ごとに設計が分岐し、RDSならそもそもアプリの仕事ではない。現状の対応は SQLite と Postgres の2種(MySQLは未対応) |
| 孤立ファイルの破棄 | まず実数を見てから設計する。誤って消すと痛い |
| 旧スキーマDBからのメタ情報回収 | `document_manager_v13.sqlite` 等が残っているため、タグ・メモ・版の鎖を引き継げる場合がある。実際に復元が必要になった局面で考える |
| アップロード失敗時のファイル削除(根本対策) | storage に削除APIが必要。S3側の扱いも決める必要がある。**照合で拾えるようになったが、増え続ける構図は変わっていない** |
| APIキーの利用クライアント記録 | 誰が古いクライアントを使っているかを把握するため |
| ディスク走査による再構築 | 照合で足りない規模の破損に対する最後の手段 |

### 既知のリスク(記録)

稼働中のSQLiteをホスト側がファイルとしてコピーすると、WALの途中を掴んで**壊れたコピー**に
なり得る。運用サーバはホスト側で `/data` のバックアップを取っているが、整合スナップショットが
無い間はこのリスクが残る。破損の検知(`GET api/db-integrity`)はできるようになったため、
気づけるようにはなっている。

## セッション(利用者の切断)

不正アクセスが疑われるときに、対象の利用者を**まとめて切る**ためのタブ。

### 決めたこと

- **切るのは一式**。セッションだけ切ってAPIキーを残すと、切ったことにならない。
  セッション・APIキー・モックアップ引換券・開いたままのSSEを同時に止める。選択式にはしない
  (不正アクセス対応で「どれを止めるか」を迷わせない)
- **単位は利用者**。セッション1件ずつの切断は置かない。一覧は判断材料として出すだけ
- **自分を切るときは、操作中のセッションだけ残す**。押した直後に自分の画面が落ちると、
  結果を確かめられない
- **切られた側には理由を伝えない**。「管理者に切断されました」と出すと、侵入者にも
  気づかれたことが伝わる。ふつうにログインが切れたときと同じ帯を出す
- **セッションIDは出さない**。一覧・履歴・アクセスログのどこにも載せない
- **切断ではできないことを、一覧より先に書く**。IDとパスワードが漏れていれば、切っても
  また入られる(IdP側でのパスワード変更が要る)。締め出しは「利用者」のタブで台帳から外す
- **履歴には、切ったセッションのIP・User-Agentも写す**。セッションと一緒に消えると、
  後から「どこから入られていたか」を追えなくなる
- **全員をまとめて切るボタンは置かない**。必要なら `SESSION_SECRET` を変えて再起動する

### やらなかったこと

| 項目 | 理由 |
| --- | --- |
| 再認証の強制(`prompt=login` / `max_age`) | IdP側のログインが残っていると、切断後もパスワードなしで再ログインできる。`auth_time` を検証すれば確実に防げるが、`auth_time` を返さないIdPでは対象者がログインできなくなる。実際のIdPで挙動を確かめてから入れる |
| 特定の利用者の締め出し | アクセス許可ユーザーから外せば足りる |

### 接続元IPについて

`trust proxy` は1段を前提にしている(手前のプロキシが1段)。2段以上の構成では全員が
外側のプロキシのIPに見えるため、導入後に一覧で自分のIPが正しく出ているかを確かめること。

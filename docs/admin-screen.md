# 管理者画面の定義

運用者(adminロール)が「異常の有無」と「次に何をすべきか」を判断できる画面の定義。
実装前の合意事項として残す。決めた理由も併記する(後から読む人が同じ判断に至れるように)。

## 目的と利用者

- **目的**: サーバーの健康状態を1箇所で把握できること。いまは機能ごとのモーダルはあるが、
  「このサーバーは正常か」を見る場所が無く、`podman inspect` や journald を見ないと分からない
  情報が多い。**SSHできない状況でも判断できること**を重視する。
- **利用者**: adminロールのみ。DBの内部状態・容量・破損情報は運用情報であり、
  アクセス許可ユーザー画面と同じ扱いにする。

## 画面の出し方

**モーダルではなくページ切替**。タブが増える前提でモーダルにすると、幅・スクロール・
情報量のすべてで無理が出る。

新しい方式は作らず、既にある `#vectorIndexPane` と同じ方式に揃える。

```css
#adminPane { display: none; flex: 1; ... }
#appShell.adminPaneMode #adminPane { display: flex; }
```

- 入口は上部バーの管理ボタン(既にadmin限定の出し分けがある)。押すと文書一覧を隠して
  管理ペインを表示し、ヘッダーに「← 文書一覧へ戻る」を置く。
- 非adminには入口が出ない。仮に到達してもAPIが403を返すため情報は出ない。
- **URLでのタブ共有・リロード復元は入れない**。ベクトル索引ペインも未対応で、
  片方だけ対応すると不統一になる。やるなら両方まとめて別途。

## タブ構成(第一弾)

第一弾は実装済み(アクセス許可ユーザー / サーバー / データベース / 変換サービス)。

| タブ | 中身 | 状況 |
|---|---|---|
| アクセス許可ユーザー | 現在のモーダルの中身をそのまま移設 | 移設のみ |
| セッション | 利用者ごとのセッション・APIキーの一覧、利用者単位の切断、切断の履歴 | 後から追加 |
| サーバー | 版 / リビジョン / ビルド時刻 / 起動時刻 / 稼働時間 / DBバックエンド | API新規 |
| データベース | 整合性確認(簡易・厳密)と最終結果、**DBと実ファイルの照合** | 一部API済 |
| 変換サービス | 到達性 / LibreOffice版 / 上限 / 変換に失敗した文書の一覧と再実行 | 一部API新規 |
| Miro 連携 | Miro のアプリの値(環境変数か画面で入力)/ 連携・連携し直し・解除 / 貼り先のボードの選択([miro.md](miro.md))。アプリの値を画面で入れられるので、管理者には常に出す | 後から追加 |

**バックアップのタブは作らない**。空のタブや「準備中」は、あるように見えて無いので害になる。

### 移設しないもの

| | 理由 |
|---|---|
| APIキー管理 | 全員が使う。管理ページに入れるとadmin専用と誤解される |
| タグ体系の管理 | 文書一覧の文脈に属する |
| 操作履歴 | 自分の操作だけで、管理機能ではない |
| ベクトル索引 | 既に独立ペインがある。動いているものを動かさない(将来タブへ統合する余地はある) |

## 必要な新規API

いずれも `requireAdmin`。

| API | 用途 |
|---|---|
| `GET api/server-status` | 版・リビジョン・ビルド時刻・起動時刻・稼働秒・DBバックエンド・DBファイル名とサイズ |
| `GET api/office-render/health` | 変換サービスの到達性(既存の `checkHealth()` を画面から見えるようにする) |
| `GET api/html-pdf/health` | PDFでダウンロード用の変換サービス(pdf-converter)の到達性。Office用とは別のコンテナなので、同じタブに別々に出す |
| `GET api/storage-reconcile` | DBと実ファイルの照合(下記) |
| `POST api/storage-reconcile/restore` | 実ファイルだけある文書をDBへ登録し直す |

`GET api/documents?renderStatus=failed` も足す。いまは絞り込みが無く、変換に失敗した文書を
探す手段が無い。これは readonly 権限のままにする(AIからも「変換に失敗した資料ある?」に
答えられるようになる)。

起動時刻は `api/version` には載せない。あちらは**公開**エンドポイントであり、
スキャンに余計な材料を与えない。

## 動作の原則

- **画面を開いただけでは重い処理を走らせない**。整合性確認と照合はボタン。開いた時点では
  起動時に実行した結果を表示する(サーバー側で最後の結果を保持する)。
- **重い操作は正体を明かす**。厳密な整合性確認は better-sqlite3 が同期APIのため
  サーバーの他の処理が止まる。確認ダイアログで明示し、業務時間外を勧める。
- **破壊的な操作は置かない**。復旧・再構築・DBの直接編集は画面に入れない。
  バックアップからの復旧はサーバー作業とする(誤操作の被害が大きすぎる)。

## DBと実ファイルの照合

### 背景: 孤立ファイルは定常的に生まれる

アップロードは「先にファイルを書き、後からDBへ登録する」順序で、
**途中で失敗したときの後始末が無い**(catch節はログを出して500を返すだけ)。
`app/lib/storage.js` には削除APIが存在しない。

つまり「実ファイルはあるのにDBに無い」は、失敗したアップロードのたびに増える。
この機能はまれな事故の保険ではなく、**日常的な掃除**も兼ねる。

→ 入口を直す(失敗時に書いたファイルを消す)ほうが根本的。ただし storage に削除APIを
足す必要があり、S3側の扱いも決まっていないため別項目とする(下記の積み残し)。

### 扱い

| 状態 | できること |
|---|---|
| 実ファイルだけある | **復元**(DBへ登録し直す)。判断材料として更新日時・サイズ・ファイル名・preview/renderの有無を出す |
| DBだけある | **報告とラベル付けのみ。削除は置かない** |

**削除しない理由**: ボリュームが未マウントのときは全件が欠損に見える。自動クレンジングは
「復旧可能な障害」を「恒久的なデータ消失」に変えてしまう。しかも失われるのはタグ・メモ・
版の鎖・アップロード者で、**ファイルからは絶対に再生できない唯一の情報**である。

### 復元の扱い

- **アーカイブ済みとして登録する**。元がアーカイブ済みだったか知る手段がないため、
  現役として復活させると一覧が汚れ、版の鎖も壊れて見える。アーカイブなら一覧は汚れず、
  必要なら既存の復元操作で戻せる。
- 全文検索テキストは再抽出する。ベクトル索引は未処理として登録し、通常の流れで追いつかせる。
- `uploaded_by` はシステム値、`uploaded_at` はファイルの更新時刻(IDの年月で妥当性を確認)。
- タグ・メモは空。

### 必須のガード

- **ストレージに到達できていない疑いがあるときは、何も報告しない**。`documents` ディレクトリが
  存在しない、または空なのにDBに大量の行がある場合は、「差異」ではなく「障害」として
  警告だけ出して照合を中止する。**これが無いとこの機能自体が凶器になる**。
- 第一弾は **local ストレージのみ対応**。S3/GCSは一覧取得のコストとページングが別問題に
  なるため、未対応を画面に明示する。
- 走査は読み取りのみ。件数上限とページングを設ける。

### 名前

画面では「**DBと実ファイルの照合**」とする。「クレンジング」は削除を含意するため使わない。
消す機能が無いのに消す語を使うと、利用者の期待と操作が食い違う。

## 積み残し

| 項目 | 理由 |
|---|---|
| バックアップ(整合スナップショット) | DB種別ごとに設計が分岐し、RDSならそもそもアプリの仕事ではない。現状の対応は SQLite と Postgres の2種(MySQLは未対応) |
| 孤立ファイルの破棄 | まず実数を見てから設計する。誤って消すと痛い |
| 旧スキーマDBからのメタ情報回収 | `document_manager_v13.sqlite` 等が残っているため、タグ・メモ・版の鎖を引き継げる場合がある。実際に復元が必要になった局面で考える |
| アップロード失敗時のファイル削除(根本対策) | storage に削除APIが必要。S3側の扱いも決める必要がある。**照合で拾えるようになったが、増え続ける構図は変わっていない** |
| APIキーの利用クライアント記録 | 誰が古いクライアントを使っているかを把握するため |
| ディスク走査による再構築 | 照合で足りない規模の破損に対する最後の手段 |
| URLでのタブ共有・リロード復元 | ベクトル索引ペインと合わせて対応する |

### 既知のリスク(記録)

稼働中のSQLiteをホスト側がファイルとしてコピーすると、WALの途中を掴んで**壊れたコピー**に
なり得る。運用サーバはホスト側で `/data` のバックアップを取っているが、整合スナップショットが
無い間はこのリスクが残る。破損の検知(`GET api/db-integrity`)はできるようになったため、
気づけるようにはなっている。

## セッション(利用者の切断)

不正アクセスが疑われるときに、対象の利用者を**まとめて切る**ためのタブ。

### 決めたこと

- **切るのは一式**。セッションだけ切ってAPIキーを残すと、切ったことにならない。
  セッション・APIキー・モックアップ引換券・開いたままのSSEを同時に止める。選択式にはしない
  (不正アクセス対応で「どれを止めるか」を迷わせない)
- **単位は利用者**。セッション1件ずつの切断は置かない。一覧は判断材料として出すだけ
- **自分を切るときは、操作中のセッションだけ残す**。押した直後に自分の画面が落ちると、
  結果を確かめられない
- **切られた側には理由を伝えない**。「管理者に切断されました」と出すと、侵入者にも
  気づかれたことが伝わる。ふつうにログインが切れたときと同じ帯を出す
- **セッションIDは出さない**。一覧・履歴・アクセスログのどこにも載せない
- **切断ではできないことを、一覧より先に書く**。IDとパスワードが漏れていれば、切っても
  また入られる(IdP側でのパスワード変更が要る)。締め出しはアクセス許可ユーザーから外す
- **履歴には、切ったセッションのIP・User-Agentも写す**。セッションと一緒に消えると、
  後から「どこから入られていたか」を追えなくなる
- **全員をまとめて切るボタンは置かない**。必要なら `SESSION_SECRET` を変えて再起動する

### やらなかったこと

| 項目 | 理由 |
| --- | --- |
| 再認証の強制(`prompt=login` / `max_age`) | IdP側のログインが残っていると、切断後もパスワードなしで再ログインできる。`auth_time` を検証すれば確実に防げるが、`auth_time` を返さないIdPでは対象者がログインできなくなる。実際のIdPで挙動を確かめてから入れる |
| 特定の利用者の締め出し | アクセス許可ユーザーから外せば足りる |

### 接続元IPについて

`trust proxy` は1段を前提にしている(手前のプロキシが1段)。2段以上の構成では全員が
外側のプロキシのIPに見えるため、導入後に一覧で自分のIPが正しく出ているかを確かめること。

# モックアップ管理の定義

LLMに作らせたWebページのモックアップ(ビルド済みの静的サイト一式)をZIPで登録し、
ブラウザでそのまま動かして確認できるようにする機能の定義。実装前の合意事項として残す。
決めた理由と、実際に試して確かめた結果も併記する(同じ検討を繰り返さないため)。

## 位置づけ

文書管理とは**別の機能**として作る。文書側は「実体は1ファイル」という前提で全体が
組まれており、多ファイルのZIPを同じ枠に入れると、入口のファイルの決め方・プレビュー・
照合(DBと実ファイルの突き合わせ)がいずれも歪む。

- **DBは同じデータベースの別テーブル**。別ファイルにするとスキーマ移行・破損検知・
  バックアップの仕組みを二重に持つことになるため
- **ファイルの置き場所は別**(`/data/mockups/<ID>/`)。文書側の照合は平らな構成を前提に
  しており、入れ子のディレクトリを見落とすため、混ぜない
- **タグ・プロジェクトは持たない**(割り切り)。文書側と別テーブルにする以上、同じタグ体系は
  共有できない
- **版管理は持つ**。モックアップは作り直して見比べる使い方が中心になるため、後から足すと
  一覧もURLも作り直しになる

## 入力と保存

| | |
|---|---|
| 登録するもの | ビルド済み一式の**ZIP** ＋ **プレビュー画像**(作成済みのものをアップロードしてもらう) |
| 展開 | **アップロード時に展開**して保存する。毎回一時展開すると、同時アクセス・後片付け・遅延が面倒になる |
| 原本 | **ZIPも残す**。ダウンロードは常にZIPを返す(容量は倍近くになるが、原本を失わないことを優先) |
| 入口 | `index.html` を規約とする |

プレビュー画像を「作成済みのものをアップロード」にしたのは、**サーバー側でブラウザを動かす
必要をなくすため**。Reactのように「JSがDOMを組み立てる」モックアップは、JSを止めて描画すると
真っ白になる。スクリーンショットを撮るには変換サービス(converter)と同じ構図の別イメージが
もう1つ必要になり、それに見合わない。`.drawio` で既に `previewfile` として画像を添える
仕組みがあるので、それを踏襲する。

## 表示のしかた(ここが設計の要)

実物は**別ウィンドウ**で開き、配信時に次のヘッダーを付ける。

```
Content-Security-Policy: sandbox allow-scripts
X-Content-Type-Options: nosniff
```

これでトップレベルのページでも**オリジンを失う**(`window.origin` が `null` になる)。
JSは動くが、このアプリのAPIにもcookieにも手が届かない。

### 別ウィンドウにするだけでは隔離にならない

ウィンドウを分けることと、権限を分けることは別物である。同じオリジンのまま配信すると、
アップロードされたJSは**ログイン中の利用者として何でもできる**(文書の削除、APIキーの発行)。
書き込み権限を持つ1人が、全員のアカウントを乗っ取れる。

### 実際に試した結果(2026-09-26)

`CSP: sandbox allow-scripts` を付けたページと、付けないページを同じ内容で配信し、
Chromiumで開いて比較した。

| | sandbox あり | sandbox なし(比較) |
|---|---|---|
| 自前のJS(相対パス) | **動いた** | 動いた |
| 自前のCSS・画像 | **読めた** | 読めた |
| `window.origin` | **null** | `http://127.0.0.1:18190` |
| アプリのAPIへの到達 | **CORSで遮断** | **読めた: cookieあり(session=...)** |

比較側が、何もしなければ何が起きるかを示している。

### オリジンを落とすと、認証も一緒に落ちる(2026-09-26に実際に踏んだ)

上の表は「APIに手が届かない」ことだけを見ていて、**モックアップ自身のファイルが
届くかどうか**を認証込みで見ていなかった。素朴に配信側へ認証を置くと、こうなる。

1. 入口のHTMLは、通常のページ遷移なのでセッションcookieが届く → 200で開ける
2. そのHTMLからのCSS・JS・画像の要求は、ページがオリジンを失っているため
   **クロスサイト扱い**になる → `SameSite=Lax` のcookieが送られない
3. 認証が通らず401 → Chromeは中身を渡さずに遮断する(`ERR_BLOCKED_BY_ORB`)

結果は**「HTMLは表示されるが、中身が何も動かない」**。エラーも出ず、ヘッダーを見ても
分からない。認証を切ると動いてしまうので、原因にも気づきにくい。いちばん厄介な壊れ方である。

### 対処: 入口で引換券を発行し、その下で配信する

```
GET /api/mockups/<ID>/view                      ← 認証が必要。ここでcookieが届く
  → 引換券を発行してリダイレクト
GET /api/mockups/<ID>/view/<引換券>/index.html  ← 引換券で認可(cookieに依存しない)
      "./app.js" は /view/<引換券>/app.js に解決される
```

**認証を外したのではなく、認証できた利用者にだけ券を渡している。** 未認証では入口を
通れないため、券は手に入らない。券は署名付き(`app/lib/mockup-token.js`)で、

- そのモックアップ**1件だけ**に効く(IDを差し替えると通らない)
- 有効期限は既定60分(`MOCKUP_VIEW_TOKEN_MINUTES`)
- 鍵は `SESSION_SECRET` から派生。偽造・期限の延長はできない

URLが漏れた場合の露出を、その1件・その時間に限定する考え方である。相対パスは券の下で
解決されるので、**モックアップ側は何も変更しなくてよい**。署名方式にしたのは、複数
インスタンス構成でも共有の保管場所が要らないため。

引換券はURLに入るため、ブラウザの履歴・サーバーのログには残る。外部への参照元漏れは
アプリ全体の `Referrer-Policy: same-origin` で止めている。

この手の「ヘッダーは正しいのに実際には動かない」は机上で気づけないため、
`test/api/mockup-view.e2e.js` で実ブラウザを開いて、モックアップ自身のファイルが
**1つも遮断されないこと**を数えて確かめている。配信側に認証を戻すとこのテストは失敗する
(実際に戻して失敗を確認済み)。

なお `.drawio` ビューアでは、iframeの `sandbox` 属性でオリジンを落とす案を一度断念している
(同一オリジンの外部スクリプトを読めなかったため。`app/server.js` の `DRAWIO_VIEWER_CSP`
付近のコメント参照)。モックアップは自分のフォルダ配下を相対パスで読むだけで事情が違い、
上表のとおり問題なく動く。

## ZIPの展開で守ること

**置き場所(パス)は厳格に、ファイルの種類は寛容に**。この2つは別の問題である。

### パスは厳格

エントリ名は、アーカイブを作る側が自由に決められる。素朴に展開すると名前のとおりの場所へ書く。

```
エントリ名: ../../../db/document_manager_v14.sqlite
          → /data/db/document_manager_v14.sqlite を上書き(メタデータが全滅する)
```

**中身が無害な .txt でも、DBファイルを上書きすれば同じ被害になる。** 拡張子では守れない。
モックアップが読むのは自分のフォルダ配下だけで正当な用途が無いため、次はすべて拒否する。

- `..` を含むエントリ、絶対パス(`/etc/...`)、ドライブレター
- バックスラッシュ区切り(`..\..\x`)
- シンボリックリンクのエントリ(リンクを作ってからその先へ書く手口)
- 展開先を組み立てた結果が、そのモックアップのディレクトリの外になるもの

### 種類は寛容

サンプルの xlsx・pdf・zip などを置いて、モックアップからダウンロードさせる使い方を想定する。
サーバーは何も実行せず静的に配るだけなので、種類を広げても危険は増えない。ただし配信時に、

- `Content-Type` は**固定表から引く**(中のファイル名を信じない)。表に無ければ
  `application/octet-stream` ＋ ダウンロード扱い
- `X-Content-Type-Options: nosniff`
- 上記の sandbox CSP

ZIPが実質「何でも入る箱」になる点は、文書側が拡張子を制限しているのと方針が変わる。
社内利用としての割り切りである。

## 上限(案。環境変数で変更できるようにする)

実測に基づく見積もり: このアプリの画面(CSS・JS込みの1枚もの)で225KB、スクリーンショットPNGが
68〜220KB。LLMが作るモックアップのHTMLは1ページ20〜60KB程度で、**50ページなら2〜11MB**。
ファイル数も容量も問題にならない規模。以下は実際の10倍程度の余裕を取っている。

| 項目 | 値 | 根拠 |
|---|---|---|
| ZIPそのもの | 100MB | 50ページ＋画像で10MB程度 |
| **展開後の合計** | **300MB** | ここが実質の防波堤。超えたら展開を中止する |
| ファイル数 | 2,000 | 50ページ＋アセットなら多くて300程度 |
| 1ファイル | 50MB | 動画を1本入れても収まる |
| 階層の深さ | 20 | `assets/img/icons/...` でも足りる |
| 圧縮率 | 展開後÷圧縮後が200倍を超えたら中止 | ZIP爆弾対策の二段目。HTMLは素直に10〜20倍に圧縮されるため誤検知しない |

絶対値(展開後300MB)が本命で、圧縮率は補助。

表示用の引換券の有効期限は `MOCKUP_VIEW_TOKEN_MINUTES`(既定60分)。短くすると
URLが漏れたときの露出は縮むが、モックアップを長く開いたままにしていると途中で
配信が止まる(開き直せば直る)。

## CDNの扱い

LLMが作るモックアップは、ほぼ必ず外部CDNを参照する(Tailwind・React等)。
**許す**方針とし、CSPで取得先を制限しない。結果として、

- **閲覧者の端末からインターネットに出られない環境では、モックアップが崩れる**
- 外部への通信自体は発生する(漏れて困るデータは持たないが、閲覧された事実はCDN側に残る)

禁止するなら `default-src 'self'` を足すだけだが、その場合はライブラリもZIPに同梱してもらう
必要がある(LLMに「CDNを使わず自己完結で」と指示すれば可能)。

## 全文検索

中のHTMLからテキストを抜く程度にする。**ビルド済みのJSに埋もれた文言は拾えない**
(Reactのように文言がJSの中にある場合)。過大な期待はしない前提。

## 画面

左のメニューに「モックアップ」を足す。文書一覧と同じ段に置くが、**別のコレクション**である
ことを示すために仕切りを入れる。

```
文書一覧  タグ体系  プロジェクト  │  モックアップ        ベクトル索引  アーカイブ
```

仕切りは `|` の文字ではなく細い縦線(`border-left` ＋ 余白)にする。文字だとリンクと同じ
大きさで主張してしまうため。

なお左右の分け方(日常的に使うもの/時々使うもの)は先に入れてある。

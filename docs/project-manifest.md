# プロジェクトの「お品書き」

## 何のためのものか

プロジェクトに資料を集めても、**集まっているだけでは中身が分からない**。
ファイル名は「要件定義書.txt」としか言わないので、受け取った側は全部開くことになる。

お品書きは、その案件にどんな資料が揃っていて、**それぞれが何なのか**を1枚で見せるもの。
人に渡すとき(引き継ぎ・レビュー依頼・打ち合わせ)にそのまま使えることを狙っている。

```
受注管理システム 再構築 お品書き

00_読みはじめ.md      まずこれを読んでください。全体像と、今回触らない範囲が書いてあります。

1. 要件
2026年6月の打ち合わせで合意した範囲です。

  要件定義書.txt      3章「受注の取消」が今回の追加分。他は現行踏襲です。
  業務フロー.txt      現行と新の対比。赤字が変わるところ。
```

## 置き場所

**プロジェクト名を押すと、プレビュー領域に出る。**

ツリーは左に残るので、構成を見ながら説明を書ける。文書を選べばプレビューに戻り、
もう一度プロジェクト名を押せばお品書きに戻る。同じ場所を使い回しているのは、
「資料を見る」と「資料の説明を読む」は同時に要らないため。

## 説明書きはプロジェクトごとに持つ

資料の説明は `project_documents.note`(プロジェクトと文書の紐づけ表)に置いている。
**文書そのものには付けない。**

1つの文書は複数のプロジェクトに登録できる。同じ設計書でも、A案件では「前提資料」、
B案件では「参考」ということがある。文書側に1つだけ持たせると、これが書けない。

文書自身のメモ(`documents.memo`)とは別物である。

| | どこに付く | 何を書くか |
|---|---|---|
| 文書のメモ | 文書そのもの | その文書についての備忘。どこから見ても同じ |
| お品書きの説明 | プロジェクトへの紐づけ | **この案件では**どういう位置づけか |

フォルダにも説明を持たせている(`project_folders.note`)。お品書きでは
フォルダが章の見出しになるため、章の前書きとして使う。

プロジェクトから資料を外すと紐づけごと消えるので、**説明も一緒に消える**。
入れ直しても前の説明は戻らない。案件での位置づけは、その案件に置いている間だけのものという扱い。

## 並び順は1か所で決める

画面とMarkdownで並びが食い違うと、渡した相手と話が合わなくなる。
並べる処理は `app/lib/project-manifest.js` に寄せ、画面もMarkdownもその結果を描くだけにしている。

並びの規則は、

1. プロジェクト直下の資料(フォルダに入っていないもの)
2. フォルダ(並び順どおり)。入れ子のフォルダはその中に続く

データが壊れていても**資料を落とさない**ことを優先している。親が見つからないフォルダは
直下として出し、文書が見つからない配置も行を残して「見つかりません」と書く。
黙って消えると「渡した一覧に載っていない資料がある」ことになり、それがいちばん困るため。

## 持ち出し

`GET /api/projects/:id/manifest.md` がMarkdownを返す。画面の「Markdownをコピー」も
これを取ってきているので、貼り付けた内容は画面と必ず一致する。

AI向けのガイドにも載せている。「この案件にはどんな資料がある?」に答えられるようにするため。

## 上限

説明1件あたり500文字(`PROJECT_NOTE_MAX_CHARS`)。ツリー取得の応答すべてに載るため、
長文は持たせない。長い説明は文書そのもののメモ側に書く。

## 権限

| | |
|---|---|
| お品書きを読む | readonly 以上 |
| 説明を書く | readwrite 以上。画面でも `readOnlyMode` では編集できない |
| 施錠中 | 書き換えは423。読む方は通す |
